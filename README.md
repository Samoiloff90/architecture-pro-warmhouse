### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут создавать новые датчики температуры через POST запрос с указанием названия, типа, локации и единиц измерения
- Пользователи могут просматривать список всех зарегистрированных датчиков с их текущими значениями и статусами
- Пользователи могут редактировать параметры датчиков (название, локация, статус) через PUT запрос
- Пользователи могут удалять датчики из системы через DELETE запрос
- Пользователи могут вручную обновлять показания датчиков через PATCH запрос
- Система поддерживает хранение метаданных каждого датчика: ID, название, тип (temperature/humidity/motion/light), локация (Living Room/Bedroom/Kitchen), текущее значение, единицы измерения, статус (active/inactive), время последнего обновления

**Мониторинг температуры:**

- Пользователи могут получать текущую температуру по названию комнаты через GET запрос /api/v1/sensors/temperature/:location
- Пользователи могут просматривать данные конкретного датчика по его ID
- Система поддерживает интеграцию с внешним Temperature API для получения актуальных данных о температуре
- Система автоматически сопоставляет локации с ID датчиков (1=Living Room, 2=Bedroom, 3=Kitchen)
- Система возвращает температурные данные в JSON формате с указанием локации, sensor ID, значения температуры, единиц измерения и временной метки

### 2. Анализ архитектуры монолитного приложения

Приложение написано на Go 1.21+ с использованием веб-фреймворка Gin для обработки HTTP запросов. База данных — PostgreSQL с единственной таблицей sensors, содержащей 9 полей (id, name, type, location, value, unit, status, last_updated, created_at).

Архитектура организована в виде трёхслойной структуры:

- Handlers layer (handlers/sensors.go) — обрабатывает входящие HTTP запросы, валидирует данные, вызывает методы моделей
- Models layer (models/sensor.go) — содержит структуру данных Sensor и методы для работы с БД (CRUD операции)
- Database layer (db/db.go) — управляет подключением к PostgreSQL

Взаимодействие между компонентами происходит через прямые вызовы функций. HTTP сервер слушает порт 8080, внешний Temperature API работает на порту 8081. Для интеграции с внешним API используется синхронный HTTP клиент в services/temperature_service.go.
Приложение развёртывается через Docker Compose, где монолит и база данных запускаются в отдельных контейнерах.

### 3. Определение доменов и границы контекстов

Выделены следующие домены (bounded contexts):

1. Device Management — управление устройствами и датчиками (создание, редактирование, удаление, хранение метаданных). Текущая реализация: таблица sensors и CRUD endpoints.
2. Telemetry & Monitoring — сбор и хранение телеметрических данных с датчиков, историческое хранение измерений, анализ временных рядов. Текущая реализация: отсутствует (нет таблицы для time-series данных).
3. Automation & Rules — создание правил и сценариев автоматизации (например, "если температура < 18°C, включить обогреватель"). Текущая реализация: отсутствует.
4. User & Access Management — управление пользователями, авторизация, разграничение прав доступа, мультитенантность. Текущая реализация: отсутствует (нет таблицы users).
5. Notification Service — отправка уведомлений пользователям через различные каналы (email, push, SMS) при срабатывании правил или критических событиях. Текущая реализация: отсутствует.

### **4. Проблемы монолитного решения**

- Ограниченная масштабируемость — невозможно масштабировать отдельные функции системы (например, только обработку телеметрии), приходится масштабировать весь монолит
- Single Point of Failure — падение приложения приводит к полной недоступности всей системы, нет изоляции отказов
- Downtime при деплое — обновление любой части системы требует перезапуска всего приложения и временной недоступности сервиса
- Отсутствие истории измерений — нет таблицы для хранения исторических данных датчиков, невозможен анализ трендов и построение графиков
- Синхронное взаимодействие с внешним API — блокирующие HTTP запросы к Temperature API снижают производительность, нет механизмов retry и fallback
- Нет мультитенантности — отсутствует изоляция данных между пользователями, невозможно развернуть систему как SaaS
- Отсутствие автоматизации — нет функционала для создания правил и сценариев, всё управление происходит вручную
- Технологическая привязка — весь код на Go затрудняет использование специализированных инструментов для разных задач (например, Python для ML-анализа данных)
- Нет observability — отсутствует structured logging, метрики, distributed tracing, что усложняет диагностику проблем в production
- Отсутствие event-driven подхода — датчики не могут асинхронно отправлять события, система работает только на основе polling

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
